## POS integration & online pre-ordering

This Website is a **separate project from the POS**. It has **no menu,
pricing, order, payment or billing logic of its own** — the POS/Firebase
project is the single source of truth. The browser only ever talks to
this site's own `/api/*` routes, which run server-side and hold the POS
API key.

### The menu is POS-only

There is **no menu file, no fallback menu and no hardcoded price** in this
repo. `lib/menu-source.ts` fetches the POS catalog and nothing else:

- Every dish shown on `/menu` is whatever the POS returns — all
  categories, all items, with the POS's own names, descriptions, images,
  prices and availability.
- The home page's "On the menu today" tiles and the chat assistant's
  answers come from the same catalog (`/api/menu-brief`).
- If the POS can't be reached, the site shows an honest
  "menu briefly unavailable" panel with the phone number. It never
  invents a dish or a price. `test/no-placeholder-prices.test.ts` fails
  the build if a literal `₹`-amount is ever added back to shipped source.
- Family combos on the home page are described but not priced — the
  figure is confirmed when the guest books.

`/menu` renders per request (`export const revalidate = 0`) so a transient
POS outage at build time can't be baked into the deploy; the catalog fetch
itself is still cached for `MENU_TTL_SECONDS`.

**POS images** are rendered with a plain `<img>`, not `next/image`. The
image host is whatever bucket the POS uses, which isn't known at build
time, so `next/image`'s `remotePatterns` allowlist isn't workable. Our own
venue photography (in `/public/images`) still uses `next/image`.

### Environment (`.env.local`, see `.env.example`)

| Variable                 | Where   | Purpose                                                            |
| ------------------------ | ------- | ---------------------------------------------------------------- |
| `POS_API_BASE_URL`       | server  | POS origin. Endpoints: `/api/website/menu`, `/api/website/orders`, `/api/website/orders/{ref}`. |
| `POS_API_KEY`            | server  | Sent as `X-API-Key`. **Never** `NEXT_PUBLIC_*`.                 |
| `ORDER_TOKEN_SECRET`     | server  | HMAC secret for per-order access tokens. Falls back to `POS_API_KEY`; set a dedicated random value in production. |
| `MENU_TTL_SECONDS`       | server  | Menu cache lifetime (default 120).                              |
| `MENU_REVALIDATE_SECRET` | server  | Optional. Lets the POS force an instant menu refresh via `POST /api/revalidate-menu`. Unset ⇒ route returns 404. |
| `PAYMENTS_MODE`          | server  | `live` (real Razorpay + POS webhook) or `mock` (local only).    |

The Razorpay **public** key id comes from the POS in the create-order
response (`payment.keyId`) — there is no Razorpay env var here. Razorpay
secrets and `WEBSITE_API_KEYS` live only in the POS project.

With `POS_API_*` unset there is no menu to show: `/menu` renders the
"menu briefly unavailable" panel and checkout replies "ordering isn't
available right now". Nothing is fabricated.

### Customer flow

Browse `/menu` → add to cart → `/cart` → `/checkout` (details) → **create
order** (POS re-prices, mints `WEB-000123`, opens a Razorpay order for the
50% advance) → **Razorpay Checkout** → `/order/WEB-000123`, which polls
the POS every 8s and shows **Order confirmed** only once the POS reports
`CONFIRMED`. `PAYMENT_FAILED` shows a clear message + a retry button.

- Menu: [`lib/menu-source.ts`](lib/menu-source.ts) — cached, tag `pos-menu`.
- POS calls: [`lib/pos-order-api.ts`](lib/pos-order-api.ts) (server only).
- Razorpay Checkout: [`lib/razorpay.ts`](lib/razorpay.ts) (browser).
- The Order ID (`ref`) is **always** generated by the POS. The Website
  never creates, chooses, or reformats it.

### Hardening

- **Order access:** reading order details needs the capability token
  ([`lib/order-token.ts`](lib/order-token.ts)) issued at creation and
  carried in the `/order/WEB-xxxxxx?t=…` link — the guessable Order ID
  alone returns 404. Token = HMAC(`ORDER_TOKEN_SECRET`, ref); stateless,
  never reveals the secret.
- **Idempotency:** checkout sends a stable `Idempotency-Key` per attempt
  (kept in `sessionStorage`, reused on retry). The Website forwards it to
  the POS and collapses concurrent repeats per instance. **The POS must
  dedupe on this key** for the cross-instance guarantee — see the
  contract note in the session checkpoint.
- **Payment retry** reuses the POS-supplied Razorpay order (safe: multiple
  attempts allowed until one succeeds; POS webhook is idempotent per
  payment id). The browser never marks an order paid/confirmed.

### Local mock

`app/mockpos/` is a stand-in POS implementing the contract: a full
40-dish catalog, order creation, and — with `PAYMENTS_MODE=mock` — a
simulated verified advance. Its order store is a JSON file in the OS temp
dir, because `next dev` runs route handlers across several worker
processes.

`npm run dev` is pinned to port **3100** so `.env.local`'s
`POS_API_BASE_URL=http://localhost:3100/mockpos` always resolves to this
app itself.

**Before deploying: delete `app/mockpos/`**, point `POS_API_BASE_URL` at
the real POS and set `PAYMENTS_MODE=live`.
